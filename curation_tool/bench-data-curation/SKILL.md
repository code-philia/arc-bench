# Bench 需求数据治理

## 范围与工作入口

阶段边界：本阶段处理需求数据协议、数据来源、逐test随机素材及必要准备交互兼容。BookStack已按后续授权接入随机名称、描述、标签和正文；不要将这一部分继续误列为未实施。回填断言补强、共享状态重复执行质量、容量检查及helper解耦等完整质量复查仍归最后实施的第6项。

仓库根目录为包含 `arc-bench/`、`curation_tool/` 和 `README_curation.md` 的目录。下文代码和产物路径均相对于仓库根目录。本技能存放在 `curation_tool/bench-data-curation/`。

## 已确认的判定标准

**具体值不等于测试数据约束。** 需求可使用具体昵称、名称、邮箱、密码、描述、正文、标签和带编号的对象作为自然示例。需求保留 one-shot 示例，测试随机生成同类输入验证行为，两者并行，不必先泛化需求。

| 内容 | 处理 |
| --- | --- |
| BookStack User、Shelf 4.1、Reference book description.、manual, handbook | 保留自然示例，不因具体值或编号而修改 |
| Click Shelves, verify Shelf list opens, then open / to return to the homepage. | 保留自然操作及验收步骤，Click、verify、create、fill 不是删除依据 |
| 已登录、已有书籍、未收藏、保存后可重新打开 | 保留自然前提和业务结果 |
| 名称/描述/正文与输入一致、持久化、父子关系、用户数据隔离 | 保留业务约束和验收强度 |
| 字段名、产品文案、默认标签、最多十条记录 | 保留产品设计；数字、预置或 seed 关键字本身不构成删除依据 |
| Seed prerequisites (prepared before this scenario) 及附属数据块 | 移除评测准备协议；必要数据改成自然示例，避免丢失字段和关系 |
| 名称必须附加 evaluator run/worker/case 后缀 | 属于评测侧命名和隔离协议，从最终需求中移除 |
| case-isolated、isolated | 结合上下文判断；仅当引用测试隔离协议时清理，不能误删业务上的数据隔离要求 |
| 初始账号、初始书架等 | 可属于正常业务内容，不因预置而删除；检查其用途和创建入口依赖 |
| role、ARIA、固定 evaluator 时钟及一般历史编辑说明 | 记录并交给总计划中的对应任务，不顺手扩大治理范围 |

相同值在自然叙述中可以保留，在附加 Seed JSON 中则可能属于重复协议；按上下文判定，不全局替换具体值。

## 清点和分类

1. 读目标 `requirements/requirements.yaml`，检查对应 tests、helpers、fixtures 中的数据和入口依赖。不得把一个场景视作后续用例的数据初始化步骤，除非实际执行框架明确如此。
2. 可用现有标准库脚本初筛：

   ```powershell
   python curation_tool/inventory_requirement_data.py bookstack
   ```

   脚本在ref/<应用>/目录生成 `data_inventory.json`，保留所有 description.text 和 Given/When/Then、所属ID、行号、原文及源哈希。它是针对当前格式的缩进扫描器，不是通用 YAML 解析器，不检查图片内容。候选词表包含 BookStack/Keep 示例词且倾向高召回，**命中不等于需要改写，未命中不代表没有问题**。
3. 语义复核所有文本，包括未命中的上下文。按完整字段记录三类决定：本项保留；含协议需局部处理；交给其他任务。对混合段说明具体处理哪句话或哪个词，避免整段删除。
4. 将分类独立保存为 `ref/bookstack/data_review.json`，必要时补中文 `data_review.md`。至少包括源文件哈希、需求/场景/步骤ID、字段、原文、行号、决定、中文理由和处理状态。统计区分字段数、协议出现次数、重复数据条目数和独立数据种类。

扫描文件会覆盖同名产物，不把唯一的人工决策保存在扫描结果中。BookStack历史分类及修改脚本绑定旧哈希和已清理的输入链，只参考方法，不能直接重放到当前需求。data_review.json是原分类基线，新增复核应保留基线来源并记录当前源哈希，不能覆盖后丢失旧决定。

## 需求修改与可选暂存

### 暂存测试协议

优先同步修改需求和测试，将必要旧信息记入ref/。只有测试暂时无法衔接且当前任务允许过渡稿时，才用 `【】` 暂存已判定协议，例如：

- `isolated Book 5.1` → `【isolated】 Book 5.1`，名称不变。
- evaluator 后缀协议 → `【原协议句子】`。
- 待厘清的特殊状态约束（例如初始书架不可变）先暂存原意，不随冗余内容直接删除。

`【】` 中是过渡备注，不属于最终产品需求。不要把业务数据本身当成协议全部包裹，也不要因加了标记就宣称最终治理完成。只处理已判定且属于本次范围的措辞。

### Seed 协议转为自然 one-shot 示例

- 比较重复数据块是否确实相同，再合并。必要时把共享示例放在 ROOT 描述；仅用于局部行为的示例放在对应需求，不要求所有应用机械地只保留两个示例。
- 用自然叙述完整表达必要数据。例如核验用户的昵称、邮箱和密码，或已有书架的名称、描述、标签及内容状态。去掉“执行场景前准备”等评测措辞和重复 JSON。
- 不把 Seed prerequisites 简单换个标题而仍逐场景重复规定初始化流程。也不删除真实示例、业务属性或创建入口所需的前提。
- 保留正常 Given/When/Then 和对象关系。重复描述中的独有属性不能静默丢弃，应保留、暂存或进一步核实。
- 对疑似无关前提，检查对应测试、helper及后续需求的真实使用后再精简。例如首页导航不使用账号，不代表后续登录可以不再拥有账号。
- 最后复查 ROOT、父需求和子需求中遗留的 `For ...:` 数据建立说明、重复示例属性、专门为评测打破初始化循环的解释等；只清理数据相关内容。

## 测试衔接与最终删除

进入测试阶段时，核对改写前后需求和相关测试；若有暂存标记或本地变更记录，一并识别原测试所依赖的信息。对可创建的对象随机生成满足业务规则的输入，通过已声明的UI建立状态，记录返回或可见的身份，再验证同一对象的名称、内容、关系、持久化及状态变化。

随机化不能削弱断言，不能只检查页面有内容。固定示例仍可留在需求中，测试不必照抄示例正文。保持合理的数据唯一性和重复执行能力，协议留在评测侧。

准备素材时兼容合理交互：例如标签可能需先展开Shelf Tags/Book Tags，可能是CSV输入也可能是Tag Name/Tag Value行。先核对reference与实际页面，不把精确Tags定位失败直接算成功能错误；兼容准备动作后再检查业务结果。BookStack的fillTags提供现有实现参考，结构化分支应明确输入数据的名/值含义。

账号、库存、历史记录等可能没有UI创建入口。先确认已有业务数据及测试如何取得可信的前提和预期结果，不擅自新增注册或管理接口，不把所有初始数据随机化后假定系统认识它们。

BookStack已确认例外：账号创建不在验收范围，使用环境提供的`admin@example.com / password`（Admin）。不要求账号随机化，不复用其他test创建的业务对象；业务素材在每个test内生成并经UI创建。用户已确认将书架入口调整为列表直接创建，不将旧helper的bootstrap依赖误当产品限制。

其中列表New Shelf是本轮用户确认后新增的外部入口，不是从reference或官方创建接口推导出的既有事实。对于其他应用，创建接口不要求父对象不等于界面一定有列表入口；详情页截图也不能证明列表按钮存在。先查reference/实际页面和需求，再记录入口调整的依据；不要无依据地增加功能范围。

### 素材模块与逐test准备

- 将纯数据生成器集中到目标tests目录下的独立TS模块，例如`tests/fixtures/data.ts`。支持默认随机、特定prefix及字段覆盖；显式空字符串不应被默认值吞掉。
- 在test回调内调用生成器，保存返回对象，用同一对象完成创建和预期值检查。不要在模块顶层或beforeAll生成可变业务对象供多个test复用；允许共享工厂函数、固定环境配置和产品文案。
- 依赖对象必须属于当前test：先创建书架再创建所属书籍，先创建书籍再准备页面或草稿。生成含父名称的资料并不等于真正创建了关联，helper必须消费相应字段。
- 不做数据库清空假设。纯数据生成、UI动作helper和环境账号各自职责清楚；无注册功能时不凭空生成可登录账号。
- 保留必要的前缀可读性，但正文、标签、描述也应来自本次生成结果。使用数据对象后同步原有断言中的预期值，不把原固定正文断言删除或改成任意非空。

### 用真实case分清失败来源

先跑少量现有REQ，确认结果可解释后按需扩大。保留失败的trace、快照及结构化运行记录，避免把模拟helper通过当作页面通过。

| 现象 | 处理原则 |
| --- | --- |
| 折叠标签导致精确Tags定位失败 | 核对reference；合理交互优先由准备helper展开并兼容字段，不能直接判产品功能错误 |
| 账号创建不在验收范围 | 使用用户确认的固定环境凭据；不能坚持所有账号必须随机化 |
| 创建功能需先有一个同类对象 | 核实是真实业务前提还是入口设计；本案例经用户确认补列表入口，不将其当普遍既有行为 |
| 点击登录不发送请求 | trace与源码确认事件未绑定时属于case代码问题，不放宽登录断言 |
| 随机描述不显示 | 对照保存响应、详情读取及渲染；本案例数据已保存，修复case遗漏渲染，而非换回固定正文 |
| 精确文案/拼写差异 | 记录需求、页面和测试差异；按当前授权处理兼容或case修正，不默认所有差异都是同一方错误 |

case源码修复和bench修改分开记录。BookStack历史case修复曾有单独授权，该授权不自动覆盖后续修改，也不要求其他应用采用同样修复。抽样通过不外推未运行用例。

测试调整并完成可用验证后，统一删除**本子任务所添加且已确认可删除的** `【内容】`，修正文句空格和标点。不要全局删除未归属本任务的括号内容。无可运行应用时记录验证限制，保留未确认标记，不把静态检查称为端到端通过。

## 修改记录与验收

按主skill逐项登记reviewed、requirements_updated、tests_updated及实际验证结果，向主skill返回需求/测试关联、暂存信息、未解决前提和最小失败证据。字段及标签准备使用当前语义接口，完整填写、读取、清空及断言均需适配；不要把已实现的contenteditable读取退回inputValue。按主skill验证选择表选择检查；fixture或准备调用有变时执行类型与素材归属检查，交互有变再补适配及相关REQ回归。验证命令、范围、结果记入checks，不以模拟归属检查代替UI回归。

临时inventory、review补充和修改日志生成在ref/bookstack内，记录源哈希和ID；阶段结束先合并永久data_review/governance_reference表及sub_progress，再由主skill清理本轮临时产物。保留trace仅限定位期间，未解决问题的最小证据先摘要进长期条目，不永久堆积运行记录。

- 共享工具统一放在 `curation_tool/`；机器可读结果、过程决定和进度统一放在 `ref/bookstack/`或`ref/`，不混入需求生成输入。
- 变更日志保存每段前后原文、需求/场景ID、阶段前后源哈希及暂存状态。旧清单可作为基线，明确它与当前源文件不同；不要使用过期行号直接操作新文件。
- 修改脚本检查输入版本，支持重复执行不重复标记，尽量保留换行及原结构。Windows写中文优先使用UTF-8文件接口或apply_patch；PowerShell向Python管道输入中文时显式设置UTF-8，避免问号损坏。
- 检查需求/场景/步骤ID和字段归属、自然示例字段及关键关系没有丢失；暂存标记成对、数量和范围可解释；协议无未处理残留；差异只在本次范围；运行`git diff --check`。
- 若本次只加标记，去掉新增括号字符应能恢复原文；若转换示例，则核对原数据字段都被保留或有明确处理决定。可用解析器时补查YAML语法，缩进扫描不等于解析验证。
- 状态区分“分类完成”“需求侧基本完成，待测试及标记收尾”“测试验证和最终清理完成”，避免提前标记整个子任务完成。

用户可明确确认“数据阶段暂结，可返工”。此时将本轮需求/测试改动、数据来源、实测范围、case修复和遗留项记录到ref/中的本地状态或进度；可复用规则才更新本技能；不擅自扩展后续任务，也不为宣称完成而删除未确认的标记。阶段暂结与最终全量验证/发布清理是不同状态。后续发现准备依赖、交互或随机素材问题时重开该阶段。
