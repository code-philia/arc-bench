# 产品交互与需求对齐

按[主流程](../bench-curation/SKILL.md)确定目标与授权，通读description、Given/When/Then、图例和相关REQ/helper。项目已有的具体产品决定见适配说明，不自动套用到其他页面或项目。不默认有例程；验证、状态及清理由主流程统一处理。

## 决定应保留的标准

| 内容 | 判定 |
| --- | --- |
| 对象身份、归属、容量、键盘可用、输入输出一致和持久化 | 保留业务含义与断言强度 |
| 明确导航、保存/取消、交互次序和状态表达 | 保留有依据的产品设计，不因可能有别的实现便自动放宽 |
| 仅方便定位的placeholder、完整可访问名称或容器协议 | 改为自然用途和可观察行为，再交role适配 |
| 依据不足或会改变产品交互 | 检查既有标准、图例和当前用户决定；不能只凭helper写法定标准 |

静态图可支持可见结构/文案判断，不能单独证明未显示的动态顺序或持久化。例程即使由用户提供，也只是被验证的实现，不是全部合法界面的定义。

按场景分别确定“展示该记录”“出现一次”“可以选择打开”的要求。例如草稿需在首页出现、但重开明确从父列表完成时，不从helper的动作型计数推导首页也必须可点击。相同类型记录能否重名由业务决定，不因定位困难新增全局唯一名称规则；测试须结合当前父对象或创建所得身份操作正确记录。

## 通过自然业务命名减少重名

发现重名时，先评估它是否混淆了用户可见的不同用途或对象类型。任务允许文案设计、已有业务依据或用户明确选择时，可用自然名称区分，例如导航Login与提交Sign in、Delete Book与Delete Page；这是产品决定，由ui确定并交role实现，不能由适配器自行改词。

命名应让用户更清楚将执行什么，不要求控件全页唯一，不添加测试编号、worker后缀、role/DOM协议，也不只为定位而强制把动态对象名拼进按钮。相同类型的多条记录仍可使用相同动作名称，按条目归属消歧；已有明确文案且未获调整授权时保留原标准。

决定改名后，同步相关父子description、scenario的When/Then、公共helper及实际评分调用；核对图例旧文案与当前文字的优先关系并记录依据，不能默默将其当等价别名。新名称成为明确要求时，旧名称不再作为替代，除非产品明确允许兼容。改名不替代owner、范围内唯一、确认目标及操作结果检查。

对应few-shot和正反例见[需求与场景同步方法](references/requirement-scenario-alignment.md)中的业务命名示例；仍有同名或错误归属时使用role的[作用域方法](../bench-role-curation/references/action-scope-compatibility.md)。两种方法可以共同使用，不能用改名掩盖定位或断言漏洞。

## 补全与一般性

检查测试涉及的用户操作和状态关系是否在需求中缺失，例如标签行准备、父子关系、保存回读和取消恢复。已有业务依据或当前用户决定成立时，补足用户、对象、动作和结果；不把Locator、DOM、role、输入框计数或helper重复fill写成产品要求。

此类任务读取[需求与场景同步方法及few-shot](references/requirement-scenario-alignment.md)。统一核对父级/叶子description、Given/When/Then和实际测试，特别是创建/编辑、保存/取消与条件分支。共性规则合理上提，文字去重交meta；未执行能力交quality登记覆盖缺口。

## 交给适配实现的契约

- 界面标签/操作文案未被明确规定时，可忽略大小写地完整匹配；明确规定的文案保留原匹配。用户输入、对象身份、正文、描述和回填值仍精确，不给包含动态对象名的整条正则加i。
- 别名和包装须有业务依据；不接受任意包含文本、Edit/Delete冒作打开入口或跨owner补足。
- 同名操作的业务范围交role实现；不将main、Actions标题或特定role设成通用必经条件，也不允许普通布局回退跳过归属约束。
- 每个放宽同时要求合理替代通过和错误实现拒绝；具体实现与结果断言分别交role、quality处理，不在本skill再建立一套适配器或验证流程。

返回明确的标准、依据、适配契约、同步的需求/scenario及待决点。大小写、别名和条件分支的反例纳入主流程验证，不能用文字同步或少量例程通过声称覆盖完整。
