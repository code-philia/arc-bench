# 补全业务交互，保持一般性并同步scenario

适用于目标需求描述遗漏测试涉及的业务操作、对象关系或可见结果的情况。“一般性”指用用户视角表达产品行为，不是删除已明确的产品交互，也不是允许一切界面实现。以下知识库few-shot仅说明判定尺度；项目产品决定另由适配说明及当前需求核实。

## 先确定哪些测试动作应进入需求

对照当前description、父子需求、scenario、图例及REQ/helper，将缺项分类：

| 来源或动作 | 处理 |
| --- | --- |
| 需求已有的业务关系/能力，测试只表达了一部分 | 补足或澄清用户动作和可见结果，修复不足的断言。 |
| 用户当前明确选择的产品交互 | 在授权范围内写入需求，保留仍适用的测试；不把一次决定推广到无关对象/控件。 |
| 图中可见的结构、文案、状态 | 可作为设计依据；静态图不能单独证明未展示的动态操作、顺序或持久化。 |
| helper的fill/click顺序、Locator、计数、等待、固定祖先路径 | 留在测试实现；不能因为已有代码如此便写成产品要求。 |
| helper重复填写未变化的数据 | 不推导出“用户必须重填才能保留原值”。 |
| 测试假设但需求未规定的排序、结构或交互 | 先判断是测试限制还是产品决定；有授权则明确后同步，没有依据则不能擅自补成新承诺。 |

这里的“架构操作”应还原为用户可观察的交互与状态关系，如标签编辑行、父子对象归属、统一保存/取消、重开回填；不由此要求数据库结构、组件框架、role或DOM。既不盲从helper，也不因界面不同自动放宽明确的产品标准。

## 用一般需求语言表达

保留“谁在什么前提下，对哪个对象做什么，会得到什么结果”。保留明确名称、业务数据、容量、可访问性、归属及持久化。删除针对某个失败实现的辩论句、评测背景和helper内部过程。

共性规则放适当父级，叶子描述保留创建/编辑等独有结果。不要把条件规则改成无条件要求，例如只明确“采用标签行时”的交互，就不能无依据禁止所有整组标签输入。也不能仅为保持测试不变，在已确定的产品标准上增加并不存在的可选分支。

## 五层同步检查

| 层次 | 核对内容 |
| --- | --- |
| 父级description | 共同业务规则、适用对象、条件和生效时机。 |
| 叶子description | 该操作的输入、目标、保存/取消结果，不与父级冲突。 |
| Given | 前置对象、归属、登录和初始状态成立，且由当前test的数据准备承接。 |
| When/Then | 写清实际验收动作和可见结果；分别核对创建/编辑、保存/取消、重开/刷新等相关分支，条件保持一致。 |
| REQ及helper | 实际执行对应动作，断言消费同一数据；能力未被执行或未被观察时记录覆盖缺口。 |

同步不等于把helper逐行翻译成scenario。辅助导航、重复fill等实现细节不必写入；能改变业务结论的动作与结果必须对应。其他依赖场景通过前置条件和有效引用继承共同规则，不为每个连带失败复制同一段文字；独立消费的子需求保留理解所需规则或引用。

若描述要求编辑时可追加空白行，但现有编辑scenario只保留已有标签，应记录“该能力为产品要求，现有场景未独立验证”，不能声称同步文字已补全覆盖。用户要求保留测试时不自动添加评分场景；发现真实矛盾应报告具体差距，不能靠模糊措辞让两边看似一致。

## Few-shot：从实现细节到需求和场景

### 1. 标签行：明确的产品选择

**输入**：图例显示空标签行及添加入口；helper先添加空行再fill，某应用要求先填名称再提交到列表。用户明确选择保留前一种交互。

**需求表述示例**：When creating or editing shelf tags in separate rows, users can add several blank rows before entering any tag names. New and existing rows remain editable, and Save Shelf saves all entered tags together with the shelf.

**场景同步**：创建保存/取消都体现现有行留空时添加空行，再填示例标签；保存检查回填/持久化，取消检查无对象产生。编辑保存/取消核对原标签保留及回填，未执行的编辑追加行单独记录。

**不要写**：“helper先click，输入框count从1变2才能通过”“为了拒绝某个应用，添加不得提交到另一列表”。用户未明确选择时，不能仅凭静态图推断空行动态行为。这个标签决定仅适用于已确定的范围，不是所有项目的通用标签规范。

### 2. 保留原标签，不强制重复输入

**输入**：helper编辑名称和描述时又fill了一遍原标签，取消后重开已检查原值。

**正确输出**：场景描述“修改名称和描述，保持原标签不变；取消并重开后显示原始名称、描述和标签”。补上已有回填断言对应的Then；不要求用户重输原标签才能保留。父级仍可要求标签可编辑，但不能声称该场景测试了标签修改或追加。

### 3. 对象归属和保存内容

**输入**：测试全页点Delete，或保存页面后只看列表标题；需求意图分别是删除当前书籍、保存标题正文。

**正确输出**：描述“选择当前书籍自己的删除操作，确认针对该书籍，完成或取消后检查对应结果”；页面场景包含重开后看到所保存标题正文。同步真实REQ/helper的归属及回读断言，具体方法使用quality子skill的[逐项约束修复](../../bench-quality-curation/references/false-acceptance-review.md)。不写“必须在main/Actions区域”“采用某个组件/存储框架”。

### 4. 业务命名减少重名

**输入**：导航入口与凭据提交都叫Login，书籍和页面的删除入口都叫Delete；当前任务允许调整产品文案。

**需求与场景输出**：可约定“选择Login打开登录表单，填写凭据后选择Sign in”；“选择当前书籍的Delete Book打开针对该书籍的确认”。适用时以Delete Page、Delete Shelf等自然对象类型区分用途，不把这些英文词强制推广为所有项目的名称。

**同步与边界**：将description、When/Then和helper/评分调用改成同一组已确定的文案，记录与旧图例的关系；保留同类多条记录的归属检查，不要求全页唯一。旧文案只有产品允许时才可保留为兼容项。

**正反例**：新导航/提交文案共存可正常登录；不同类型删除名称共存可选对对象。明确新文案时旧名称不能替代；两个同名新提交按钮仍拒绝；子页面错误地写着Delete Book也不能冒作书籍操作。改名后仍验证确认目标和完成/取消结果，不只检查新文字出现。

## 验证与归因

实际解析YAML，比较需求/场景/步骤/图片ID、层级、引用和评分身份。仅润色及对齐已有动作时记录测试无需变更；用户要求测试不变时可比较文件哈希。若实际操作/预期改变，则按授权同步测试，并做适配正反例及相关回归，不只做结构检查。

记录失败阶段及其性质：用户明确产品决定后，应用不满足应保留失败；不能继续称为必须放宽的测试兼容缺口。旧运行是在旧描述下得到的证据，不追溯宣称旧需求已明确全部行为，也不因改了文字就更新通过数。模拟、定向、全量和未验证分支分别报告，本地决定和证据统一放ref/。
